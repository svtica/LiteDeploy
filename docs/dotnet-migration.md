# Migrating LiteDeploy to .NET 10: assessment

*November 2026.*

## Current state

| Item | Value |
|---|---|
| Language | C# (`LangVersion` 7.3 in x64, compiler default in x86) |
| Projects | One: `LiteDeploy.csproj`, WinForms exe, about 9,600 lines |
| Format | SDK-style project since this assessment (formerly the old MSBuild format with ClickOnce leftovers) |
| Framework | .NET Framework 4.8 (`net48`) |
| Configurations | `Debug` and `Release`, `x86` (actually AnyCPU or x64 depending on the configuration) and `x64` |
| Dependencies | Framework assemblies only, plus a COM reference to `WindowsInstaller` (msi.dll, interop generated by tlbimp and embedded) |
| Precompiled DLLs | None |
| Third-party tools at run time | `PsExec` (Sysinternals, not redistributed); `RDPWInst.exe` and `RemoteManagement.msc` (optional) |

## Cost outside the code

- **Runtime**: .NET Framework 4.8 ships with Windows 10 and 11 and follows their lifecycle. A
  `net10.0-windows` application needs the **.NET Desktop Runtime 10** on every admin workstation, or a
  self-contained publish of about 60 to 150 MB instead of about 1 MB today.
- **Support**: .NET 10 LTS is supported until November 2028, so another migration (.NET 12 or later)
  would follow about two years later. .NET Framework 4.8 has no announced end of support outside the
  Windows lifecycle.
- **Suite**: LiteTask and LitePM are .NET Framework 4.8 too. Moving LiteDeploy alone adds one more
  runtime to the workstations, with no benefit for the suite.
- **Tests**: no automated tests; a full manual pass (deployment, MSI, AD, ping, DNS scan, reports) and
  a run of the lot 1 soak test are needed.

## Estimate

| Item | Effort |
|---|---|
| Code fixes (`Thread.Abort`, MSI, `Process.Start`, references) | 1.5-2.5 d |
| Binary resources (check or regenerate) | 0.5-1 d |
| Project, CI, package (runtime or self-contained publish), LiteTask contract | 0.5-1 d |
| Testing and soak run | 1-2 d |
| **Total** | **about 4 to 6 days**, plus deploying the runtime to the workstations |

## Recommendation

**Do not migrate to .NET 10 now.** The benefit is small for a lightly developed admin tool used on a
few workstations (comparable WinForms performance, no expected feature that needs it), and the cost is
real: a runtime to deploy or a 60-150 times larger package, another migration when .NET 10 support
ends, and divergence from LiteTask and LitePM.

Instead:

1. the project now uses the **SDK format while staying on `net48`**: readable project,
   `msbuild -restore`, ready for a future migration that will come down to changing `TargetFramework`
   and fixing the blockers above;
2. a temporary comparison workflow proved that the build output is identical (removed before merging).

If the migration becomes desirable (for example when the whole suite moves to .NET), start by removing
the three `Thread.Abort` calls and the COM reference: those changes are valid under .NET Framework too
and reduce the migration to a project change.
